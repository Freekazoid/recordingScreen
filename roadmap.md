# Roadmap — Screen Recorder v4 (rewrite)

> **Назначение:** единый план этапов, задач и статусов. Обновляется по ходу
> работы. Любая задача, меняющая scope/архитектуру, сначала попадает сюда,
> затем — в код.
>
> **Текущий этап:** Discovery → Rewrite bootstrap (решения по стеку приняты)
> **Целевой результат:** Screen Recorder 4.0 — кроссплатформенное приложение
> с Rust-ядром, нативным Rust-интерфейсом (egui) и Python ML-sidecar:
> надёжная запись, раздельные аудиодорожки, качественная транскрипция и
> диаризация.
> **Последнее обновление:** 2026-11-04

---

## Решения пользователя (2026-11-04)

| Вопрос | Решение |
|---|---|
| Стратегия | **Полный rewrite** с учётом существующего кода; новая мажорная версия |
| UI/ядро | **Rust + нативный UI**; рекомендуется **egui/eframe**, Go + Wails — альтернатива |
| Облако | **Offline + опциональное облако** (по умолчанию локально) |
| Приоритет ОС | **Linux-first**, первый инкремент — **X11 + Wayland** |
| GPU | **CPU по умолчанию + опциональный GPU-пак** |
| Git | Ветка `rewrite/v4` в текущем репозитории, legacy-тег, версия `4.0.0-alpha.1` |

> **Рекомендация архитектора:** Rust + **egui/eframe** (MIT/Apache-2.0).
> Нативный UI без WebView, малый бинарник, простая интеграция с Rust-ядром.
> Slint отклонён из-за GPLv3/коммерческой лицензии; iced — из-за меньшего
> набора готовых компонентов для таблиц/редактора. Go + Wails — альтернатива,
> но для WGC/ScreenCaptureKit/PipeWire в Go потребуется больше cgo/внешних
> утилит. Финальный выбор UI-фреймворка подтвердить до этапа 1.

## 0. Паспорт проекта (PMBOK: Initiating)

| Параметр | Значение |
|---|---|
| Продукт | Screen Recorder 4.0 |
| Владелец продукта | Пользователь (Freekazoid) |
| Целевые ОС | Linux (primary), Windows, macOS |
| Тип поставки | Десктопное приложение, локальная обработка |
| Ядро | Rust (рекомендуется) или Go |
| UI | **egui/eframe** (нативный Rust, MIT/Apache); Wails — альтернатива для Go |
| ML | Python 3.12 sidecar: faster-whisper, pyannote, Vosk |
| Медиа | ffmpeg/ffprobe (bundled) |
| Хранение | SQLite (WAL) + файловые артефакты |
| Ограничение | Без изменения системных настроек и без root/admin |
| Бюджет | 28–38 человеко-недель (1 разработчик — 7–9 месяцев) |
| Критерий успеха MVP | 99% записей с валидным звуком; WER ≤ 10%; DER ≤ 15%; 0 ошибок прав в релизе |

### Scope MVP (что входит / не входит)

**Входит:**

- запись экрана/окна/области/аудио с раздельными дорожками system/mic;
- preflight-проверка прав, устройств и уровня сигнала;
- надёжная транскрипция (faster-whisper, auto-язык, VAD, тишина);
- channel-aware диаризация + pyannote, ручное переименование;
- job-модель, история, восстановление после падения;
- единый data dir, кроссплатформенные пути;
- Linux (X11/Wayland) полностью; Windows/macOS — базовые сценарии;
- нативный Rust-интерфейс (egui) с экранами записи, истории, транскрипта,
  настроек.

**Не входит:**

- облако по умолчанию, аккаунты, совместная работа;
- realtime-транскрипция;
- мобильные приложения;
- микросервисы/серверная инфраструктура;
- шифрование записей at-rest (post-MVP).

## 1. Git-стратегия и версия

**Цель:** начать заново, не потеряв рабочую версию 3.2.194.

| Шаг | Действие |
|---|---|
| 1 | Зафиксировать текущее состояние: тег `v3.2.194-legacy` (или `legacy-3.2.194`) |
| 2 | Создать ветку `rewrite/v4` от `main` |
| 3 | Поднять версию до `4.0.0-alpha.1` |
| 4 | Новый код — только в `rewrite/v4`; `main` остаётся рабочим 3.x |
| 5 | После Gate G7 — merge в `main`, тег `v4.0.0` |
| 6 | Историю не переписывать (no force-push), старые теги сохранить |

Если нужен отдельный репозиторий — сделать mirror `recordingScreen-v4`,
но по умолчанию оставляем один репозиторий и ветку.

**Правило коммитов:** без `Co-Authored-By` и любых трейлеров авторства
(см. `AGENTS.md`, хук `.githooks/commit-msg`).

## 5. Этап 2 — Recording core (Rust)

**Цель:** запись, которую нельзя «потерять» и в которой слышно, что происходит.

### Задачи

- [ ] **R-01.** Домен `Session`, `Track`, `Device`, `SessionManifest`; state machine.
- [ ] **R-02.** Порты `ScreenCapture`, `AudioCapture`, `LevelMonitor`; Rust traits.
- [ ] **R-03.** Linux X11: ffmpeg `x11grab`/`xcap`; area/window.
- [ ] **R-04.** Linux Wayland: `ashpd` portal + PipeWire; fallback `wf-recorder`; app-id.
- [ ] **R-05.** Windows: WGC/`ddagrab`; WASAPI loopback + mic; fallback `gdigrab`/`dshow`.
- [ ] **R-06.** macOS: ScreenCaptureKit/`avfoundation`; CoreAudio tap/BlackHole; TCC.
- [ ] **R-07.** Раздельные дорожки: `system.wav`, `mic-<device>.wav`, `mix.wav` (dual-mono).
- [ ] **R-08.** Preflight: 1-секундная проба, RMS/peak, статус «тихо/нет сигнала/нет прав».
- [ ] **R-09.** Индикаторы уровня в UI + кнопка «Проверить звук».
- [ ] **R-10.** Синхронизация: общий `t0`, `start_offset_ms`, проверка ≤ 100 мс.
- [ ] **R-11.** Сегментированная запись (60 с) + concat; восстановление после kill -9.
- [ ] **R-12.** Валидация output dir: write-probe, свободное место, fallback.
- [ ] **R-13.** Манифест: устройства, бэкенды, версии, уровни, хэши.
- [ ] **R-14.** Политика тишины: silent track не блокирует остальные.
- [ ] **R-15.** Смена устройства/наушников: детект и предупреждение.

### Gate G2 — запись

- [ ] 30-минутная запись на Linux X11/Wayland; дорожки валидны, sync ≤ 100 мс.
- [ ] Нет записи в CWD/install.
- [ ] Замьюченный микрофон → предупреждение, system продолжает работать.
- [ ] Тихий system → mic продолжает работать.
- [ ] `kill -9` → сессия восстанавливается.

## 6. Этап 3 — Processing pipeline (Rust)

**Цель:** обработка, которую можно закрыть и продолжить.

### Задачи

- [ ] **P-01.** SQLite-схема: sessions, tracks, jobs, job_steps, artifacts, speakers, crashes.
- [ ] **P-02.** `JobRepository` + state machine, идемпотентные шаги, retry/backoff.
- [ ] **P-03.** Worker-процесс/ Tokio tasks + очередь; события в UI.
- [ ] **P-04.** Восстановление: `running` → `queued`, `recording` → `interrupted`.
- [ ] **P-05.** ffmpeg-пайплайн: concat, loudness normalize, resample 16k, mix, export.
- [ ] **P-06.** Проверка результата: длительность, потоки, размер, RMS; repair.
- [ ] **P-07.** Очистка temp по TTL; исходные дорожки не удалять.
- [ ] **P-08.** История сессий: статус, ошибка, повтор, открыть папку.
- [ ] **P-09.** Метрики: время шагов, RTF, RAM/VRAM.

### Gate G3 — обработка

- [ ] Убийство приложения в середине обработки → job продолжается.
- [ ] Повторный шаг не дублирует артефакты.
- [ ] Исходные дорожки сохраняются до успешного экспорта.
- [ ] Пользователь видит шаг и прогресс.

## 7. Этап 4 — ML sidecar (Python)

**Цель:** точный текст и устойчивое разделение спикеров, не ломая Rust-ядро.

### Задачи

- [ ] **A-01.** `ml-sidecar` CLI: `transcribe`, `diarize`, `serve --stdio`.
- [ ] **A-02.** JSON-RPC 2.0: `hello`, `asr.transcribe`, `diarize.run`,
  `models.status`, `cancel`, `shutdown`; progress/notifications.
- [ ] **A-03.** faster-whisper адаптер; auto-язык; VAD Silero; word timestamps.
- [ ] **A-04.** Длинные файлы: окна с overlap, дедупликация слов.
- [ ] **A-05.** pyannote community-1/3.1; `exclusive`; ограничения спикеров.
- [ ] **A-06.** NeMo Sortformer — опциональный адаптер; Vosk — fallback.
- [ ] **A-07.** Rust `TranscriptMerger`: channel-aware system/mic, overlap, echo.
- [ ] **A-08.** Speaker naming: enrollment, эмбеддинги, ручное переименование.
- [ ] **A-09.** Экспорт: TXT, MD, SRT, VTT, JSON.
- [ ] **A-10.** Регрессионный корпус + WER/DER отчёт.
- [ ] **A-11.** Sidecar health/restart; таймауты; отмена; логи stderr.
- [ ] **A-12.** Переиспользовать проверенные Python-алгоритмы из 3.x, но
  отвязать от GUI/настроек/ФС.

### Gate G4 — качество

- [ ] WER ≤ 10% на чистой русской речи (корпус ≥ 30 мин).
- [ ] DER ≤ 15% на 2–4 спикерах (корпус ≥ 30 мин).
- [ ] Тихая валидная запись не помечается тишиной (> 98%).
- [ ] Sidecar переживает перезапуск; прогресс и отмена работают.
- [ ] Ручное переименование сохраняется в экспорте.

## 15. Управление изменениями

1. Любая новая функция/изменение архитектуры → задача в roadmap + ADR.
2. Изменение scope MVP → отметка в `PROJECT_MEMORY.md` и пересмотр Gate.
3. Код не пишется без задачи и критериев приёмки.
4. После каждого этапа — обновление статусов `[x]`, журнала и метрик.
5. Откат: legacy-тег 3.2.194 и ветка `main` остаются рабочими.
